# Interface localization (i18n)

How the web client renders its interface strings in more than one language,
how to add a locale, and what must never be translated. Part of #51 / epic
#53. The model's reply language is a separate concern owned by the worker;
this document covers only the chrome around the reply.

## How it works

- **Public surface.** Everything is imported from `@/i18n`
  (`src/i18n/index.ts`); only the tests inside `src/i18n` reach into the
  submodules.
- **One registry.** `LOCALES` in `src/i18n/locales.ts` maps each tag to its
  dictionary, its native display name (what the language picker shows:
  `English`, `Português (Brasil)`) and its BCP 47 primary subtags
  (`{ en: { dictionary: en, displayName: "English", primaries: ["en"] },
"pt-BR": { dictionary: ptBR, displayName: "Português (Brasil)", primaries:
["pt"] } }`). `Locale`, `SUPPORTED_LOCALES`, `t()`, `normalizeLocale()` and
  `toResponseLanguage()` are all derived from it; `DEFAULT_LOCALE = "en"`.
- **Dictionaries, no library.** `src/i18n/en.ts` is the typed source of truth
  (`as const`, exporting `MessageKey` and `Dictionary`). Every other locale
  file is typed `satisfies Dictionary` so a missing or extra key fails `tsc`.
  `src/i18n/i18n.test.ts` enforces parity at runtime for every registered
  locale, rejects empty values, and rejects any non-English value that is
  byte-identical to the English one (outside a small proper-noun allow-list).
- **Keys are semantic**, not the English text: `thread.welcome`,
  `composer.placeholder`, `error.connectionLost`. Controls and actions are
  named for what they are or do (`userMenu.trigger`, `composer.voiceButton`,
  `thread.scrollToBottom`, `globalError.retry`), never for the ARIA attribute
  they feed. Suggestion chips have a `label` key (what the user sees) and a
  separate `prompt` key (what is sent to the model), because the prompt must
  be idiomatic model input in each language, not a translation of the label;
  `thread.tsx` derives both from one chip id so they cannot be mispaired.
- **`t(locale, key)`** in `src/i18n/t.ts` is two property lookups, for code
  that is not React (the global error boundary). There is no interpolation
  (no shipped key needs one) and no missing-key branch: `MessageKey`,
  `satisfies Dictionary` and the parity test make a miss unreachable.
- **`normalizeLocale(input)`** maps any language tag the worker or browser
  hands us onto a `Locale` by rule: canonicalize (trim, `_` → `-`, case-fold),
  exact match against `SUPPORTED_LOCALES`, then primary-subtag match against
  the registry, then `DEFAULT_LOCALE`. So `pt` / `pt-BR` / `PT-br` / `pt_BR` /
  `pt-PT` → `pt-BR`, `en` / `en-US` → `en`, anything else (including
  `undefined`) → `en`. Only `navigator.language` is consulted;
  `navigator.languages` (the ordered list) and `Accept-Language` are not.
- **`toResponseLanguage(locale)`** is the inverse for the worker: the
  registry's first primary subtag, an ISO 639-1 code (`pt-BR` → `pt`,
  `en` → `en`). The worker validates `response_language` against
  `/^[a-z]{2}$/` (`user-do.ts`, `ISO_639_1_PATTERN`), so the full tag must
  never be sent. `i18n.test.ts` checks that every locale's code matches
  that pattern and round-trips through `normalizeLocale()`.
- **`getInitialLocale()`** is the locale known before any browser signal:
  `NEXT_PUBLIC_DEFAULT_LOCALE` (build-time; lets staging pin `pt-BR`) or
  `DEFAULT_LOCALE`. The root layout renders `<html lang>` with it, the
  provider uses it as its server snapshot, and `global-error.tsx` renders it.
- **`LocaleProvider`** (`src/i18n/locale-provider.tsx`) holds the locale in
  React context and exposes `useLocale()` → `{ locale, setLocale, t }` and
  `useT()` → `(key) => string` (the same `t` function, rebuilt once per
  locale change and shared by every consumer). It is mounted once in
  `src/app/layout.tsx`.
- **Hydration-safe seeding.** `NEXT_PUBLIC_*` is inlined into both bundles,
  so the server render and hydration both use `getInitialLocale()` and always
  agree. With no pin, the browser's `navigator.language` takes over right
  after hydration through `useSyncExternalStore` (server snapshot =
  `getInitialLocale()`, client snapshot = pin or browser): no hydration
  mismatch and no flash for English users. `locale-provider.test.tsx`
  hydrates real server markup and asserts no recoverable error.
- **`<html lang>`** follows the locale: the provider writes
  `document.documentElement.lang` in a layout effect, so the attribute changes
  in the same frame as the text it describes.
- **The runtime hook is locale-agnostic.** `use-chat-runtime.ts` never holds
  copy. It exposes `status: { key: "status.connecting" } | { text: <worker
status> } | null` and attaches `metadata.custom.errorKey`
  (`"error.generic"` | `"error.connectionLost"` | `"error.timeout"`) to the
  canned error turns it appends, whose text content is empty. `thread.tsx`
  translates both at render, so a locale change re-renders them and the
  streaming code (`handleComplete`, `finalizeComplete`, `handledTerminal`) is
  untouched.
  Worker status `message` is rendered as-is: the worker localizes it from
  the same stored preference (bt-servant-worker#407), so the client never
  translates status text.
- **`global-error.tsx`** replaces the root layout (and with it the provider),
  so it renders `getInitialLocale()` via the pure `t()` and declares that
  locale on its own `<html>`.

## The language preference

One setting, coupled: the interface locale and the model's reply language are
the same preference. The worker stores it as `response_language` (ISO 639-1,
`pt`), the BFF proxies it at `GET`/`PUT /api/preferences`
(`src/app/api/preferences/route.ts`), and the client maps in both directions
with `normalizeLocale()` (`pt` → `pt-BR`) and `toResponseLanguage()`
(`pt-BR` → `pt`). The user chooses; nothing else writes the preference (the
worker's per-turn language detection is telemetry only).

- **Load and first-visit seed** — `usePreferredLocale()`
  (`src/hooks/use-preferred-locale.ts`), mounted once by `AssistantProvider`,
  i.e. in the authenticated area only (the BFF route needs a session). On
  mount it `GET`s the preference: a stored value is applied with
  `setLocale(normalizeLocale(it))` (an explicit choice beats the browser; an
  unsupported code falls back to `en` for the chrome only). Nothing stored
  means a first visit on any device: the browser-derived locale is written
  back with one `PUT { response_language: toResponseLanguage(locale) }` so
  it follows the user to other devices. There is exactly one write per user,
  not per visit: only the mount whose `GET` came back empty writes, later
  visits find the value stored, and an unmount aborts the in-flight request
  (StrictMode's double effect run therefore also produces one `PUT`).
  Failures (`GET` or `PUT`) are logged with `console.error` and context and
  leave the browser locale in place; there is no silent catch and no crash.
- **Never mid-stream** — the hook takes `{ paused }`, which
  `AssistantProvider` feeds with `isLoading`. A preference that arrives while
  a reply is streaming is held and applied when the stream ends, so the
  chrome never flips under an animating reply.
- **Picker** — the user menu (`src/components/user-menu.tsx`) renders a
  `Language` label (`userMenu.language`) and a `DropdownMenuRadioGroup` over
  `SUPPORTED_LOCALES`, each item showing the registry's `displayName`, the
  current locale checked. Selecting one calls
  `saveLocalePreference(locale)` (the `PUT`) and then `setLocale`, so the
  whole tree re-renders in the new locale without a reload; on failure the
  cause is logged and the current locale stays (the radio is controlled by
  `locale`, so it snaps back). Display names are not translation targets:
  each language is named in itself, and the names live in the registry, not
  in JSX, so the lint guard needs no allow-list entry for them.
- **Status key** — worker status events carry `key` (bt-servant-worker#407:
  `status_queued`, `status_processing`, `status_preparing`,
  `status_executing_tools`, `status_transcribing`, `status_tts_generating`,
  `status_tts_still_generating`). `use-chat-runtime.ts` extends the
  inactivity window when `key` starts with `status_tts_`; when no `key` is
  present (an older worker) it falls back to the English keyword match on
  `message`. Nothing else reads `key`; the localized `message` is what the
  status line shows.

## Never translate

These two strings are **data, not copy**. Translating them breaks behavior.

1. **`"[Voice message]"`** (`VOICE_MESSAGE_SENTINEL` in
   `src/lib/voice-message.ts`) — written by `use-chat-runtime.ts` as the
   user message text when a voice turn has no transcript, persisted in chat
   history, and compared by equality in `thread.tsx` to decide whether to
   render the voice label. The _label_ shown to the user is the dictionary
   key `message.voiceMessage`; the sentinel itself stays English forever.
   One test anchors the literal (`use-chat-runtime.test.ts`).
2. **The SSE status TTS test** in `use-chat-runtime.ts`: the
   `status_tts_` key prefix and, for worker versions that send no `key`, the
   English keyword fallback (`includes("audio" | "tts" | "speech")`). Both
   extend the inactivity timeout during TTS; both are protocol, not copy.

## Deliberately left in English

- `metadata.title` / `metadata.description` in `src/app/layout.tsx` — resolved
  on the server before any client locale is known; localizing it needs
  server-side locale detection (out of scope).
- `formatBytes` unit labels (`B`, `KB`, `MB`, …) in `src/lib/utils.ts` — units.
- Product names: `BT Servant`, `BTS Web`, and the version footer
  `BT Servant Web vX.Y.Z`.

## Adding a locale

1. Create `src/i18n/<tag>.ts` exporting a dictionary typed
   `satisfies Dictionary` (copy `pt-BR.ts` as a template). `tsc` fails until
   every key is present.
2. Add one entry to `LOCALES` in `src/i18n/locales.ts` with the dictionary,
   the native `displayName` and the primary language subtags that should
   resolve to it (the first is what the worker stores). `Locale`,
   `SUPPORTED_LOCALES`, `t()`, `normalizeLocale()`, `toResponseLanguage()`
   and the picker pick it up from there.

Then run `npm test`: the parity, empty-value and untranslated-value checks
run for every registered locale automatically. Add rows for the new tag to
the `normalizeLocale` table in `src/i18n/i18n.test.ts`, add any proper noun
that legitimately stays identical to `IDENTICAL_VALUE_ALLOWLIST` there, and
get a native-speaker review in situ on staging
(`NEXT_PUBLIC_DEFAULT_LOCALE=<tag>`) per the checklist below. The UI suites
(`thread.test.tsx`) already run once per supported locale.

## Adding or changing a string

1. Add the key to `src/i18n/en.ts` (semantic name, English value).
2. Add the same key to every other locale file — `tsc` enforces this.
3. Use it: `const t = useT(); t("my.key")` in components, or
   `t(locale, "my.key")` outside React. In `use-chat-runtime.ts`, store the
   key (`status`, `errorKey`) and let the thread translate it.
4. Never write the English text inline in JSX. The lint guard below fails
   the build if you do.

## Lint guard

`eslint.config.mjs` applies to `src/components/**/*.tsx`, `src/app/**/*.tsx`
and `src/hooks/**/*.{ts,tsx}` (tests excluded):

- `react/jsx-no-literals` (`noStrings: true`, `ignoreProps: true`) — rejects
  JSX text children and `{"literal"}` expression containers. `ignoreProps`
  is `true` because with `false` the rule reports every string attribute
  (`className`, `type`, svg `d`, …) and has no per-attribute filter.
- `no-restricted-syntax` selectors — reject string and template literals in
  user-facing attributes (`aria-label`, `placeholder`, `title`, `alt`,
  `tooltip`, …), in both the `attr="…"` and `attr={"…"}` / ``attr={`…`}``
  forms, and string or template literals in ternary / logical expressions
  inside JSX, which `jsx-no-literals` does not see.
- `allowedStrings`: `·` (glyph), `BT Servant`, `BTS Web` (product names).
  Add to this list, with a comment, only for strings that are genuinely not
  translation targets. Do not `eslint-disable` inline. The test-side
  proper-noun allow-list (`IDENTICAL_VALUE_ALLOWLIST` in `i18n.test.ts`) is
  kept separately: the ESLint config is plain `.mjs` and cannot import a
  TypeScript constant without a loader.

Both rules only see JSX. A string that a hook or `src/lib/**` module
_returns for display_ is not caught; those layers are convention-only, and
the convention is that they return keys (see the runtime hook above), not
copy. For `use-chat-runtime.ts` the convention is pinned by a test that scans
its source for every dictionary value of every locale (the
`"[Voice message]"` sentinel excepted).
`eslint-plugin-i18next/no-literal-string` was not adopted: it is an extra
dependency and the current selectors already cover the shapes that occur in
this tree (verified with a probe file of every shape). Template literals count
as copy only when their static text contains letters; `${m}:${s}` is a value.

## Review checklist for a new locale or new strings

- [ ] Every key present in every locale file (`npm run typecheck`,
      `npm test`).
- [ ] No value is byte-identical to English unless it is a proper noun on
      the allow-list.
- [ ] Register and tone match the product voice: natural, not machine-stiff;
      for pt-BR the "você" form.
- [ ] Suggestion-chip prompts read as something a native speaker would
      actually type to the model, not as label translations.
- [ ] Punctuation and ellipses follow the language's conventions.
- [ ] Strings fit their controls (chips, menu items, aria labels) without
      truncation on a narrow viewport.
- [ ] `"[Voice message]"`, the `status_tts_` key test and its keyword
      fallback are untouched.
- [ ] The new locale has a native `displayName` in the registry and appears
      in the user menu's picker.
- [ ] Reviewed in situ on staging by a native speaker, not only in the diff.
