# Interface localization (i18n)

How the web client renders its interface strings in more than one language,
how to add a locale, and what must never be translated. Part of #51 / epic
#53. The model's reply language is a separate concern owned by the worker;
this document covers only the chrome around the reply.

## How it works

- **Locale model.** `Locale = "en" | "pt-BR"` in `src/i18n/types.ts`, with
  `SUPPORTED_LOCALES` and `DEFAULT_LOCALE = "en"`.
- **Dictionaries, no library.** `src/i18n/en.ts` is the typed source of truth
  (`as const`). Every other locale file is typed
  `satisfies Record<MessageKey, string>` so a missing or extra key fails
  `tsc`. `src/i18n/i18n.test.ts` enforces parity at runtime as well, rejects
  empty values, and rejects any non-English value that is byte-identical to
  the English one (outside a small proper-noun allow-list).
- **Keys are semantic**, not the English text: `thread.welcome`,
  `composer.placeholder`, `error.connectionLost`. Suggestion chips have a
  `label` key (what the user sees) and a separate `prompt` key (what is sent
  to the model), because the prompt must be idiomatic model input in each
  language, not a translation of the label.
- **`t(locale, key, params?)`** in `src/i18n/t.ts` is a pure lookup with
  `{param}` interpolation, for code that is not React (the runtime hook's
  status and error strings). A missing key throws outside production and
  returns the key itself in production.
- **`normalizeLocale(input)`** maps any language tag the worker or browser
  hands us onto a `Locale`: `pt` / `pt-BR` / `PT-br` / `pt_BR` → `pt-BR`,
  `en` / `en-US` → `en`, anything else (including `undefined`) → `en`.
- **`LocaleProvider`** (`src/i18n/locale-provider.tsx`) holds the locale in
  React context and exposes `useLocale()` → `{ locale, setLocale }` and
  `useT()` → `(key, params?) => string`. It is mounted once in
  `src/app/layout.tsx`.
- **Hydration-safe seeding.** The server render and hydration always use
  `en`; on the client the locale is seeded from `NEXT_PUBLIC_DEFAULT_LOCALE`
  if set (lets staging pin `pt-BR`), otherwise from `navigator.language`.
  The seed is read through `useSyncExternalStore` with a server snapshot of
  `en`, so no hydration mismatch and no flash for English users.
- **`<html lang>`** follows the locale: `layout.tsx` renders
  `lang={DEFAULT_LOCALE}` for SSR and the provider sets
  `document.documentElement.lang` on every change.
- **`global-error.tsx`** replaces the root layout (and with it the provider),
  so it renders the default locale via the pure `t()` and declares
  `lang={DEFAULT_LOCALE}` on its own `<html>`.

Later work (#51 PR 3) only needs to call `setLocale(normalizeLocale(...))`
from the `complete` SSE event and from the preferences GET; no other wiring
is required.

## Never translate

These two strings are **data, not copy**. Translating them breaks behavior.

1. **`"[Voice message]"`** — written by `use-chat-runtime.ts` as the user
   message text when a voice turn has no transcript, persisted in chat
   history, and compared by equality in `thread.tsx` to decide whether to
   render the voice label. The _label_ shown to the user is the dictionary
   key `message.voiceMessage`; the sentinel itself stays English forever.
2. **The SSE status keyword heuristic** in `use-chat-runtime.ts`
   (`statusLower.includes("audio" | "tts" | "speech")`) that extends the
   inactivity timeout during TTS. It matches worker status text; the worker
   will replace it with a structured `key` (bt-servant-worker#405) and PR 3
   switches to that.

## Deliberately left in English

- `metadata.title` / `metadata.description` in `src/app/layout.tsx` — resolved
  on the server before any client locale is known; localizing it needs
  server-side locale detection (out of scope).
- `formatBytes` unit labels (`B`, `KB`, `MB`, …) in `src/lib/utils.ts` — units.
- Product names: `BT Servant`, `BTS Web`, and the version footer
  `BT Servant Web vX.Y.Z`.

## Adding a locale

1. Add the tag to the `Locale` union and to `SUPPORTED_LOCALES` in
   `src/i18n/types.ts`.
2. Create `src/i18n/<tag>.ts` exporting a dictionary typed
   `satisfies Record<MessageKey, string>` (copy `pt-BR.ts` as a template).
   `tsc` fails until every key is present.
3. Register it in the `dictionaries` map in `src/i18n/t.ts`. `tsc` fails
   until the new union member has an entry.
4. Teach `normalizeLocale()` in `src/i18n/t.ts` which primary language subtags
   map to it, and add rows to the `normalizeLocale` table in
   `src/i18n/i18n.test.ts`.
5. Run `npm test` — the parity, empty-value and untranslated-value checks
   cover the new file automatically. Add any proper noun that legitimately
   stays identical to the `IDENTICAL_VALUE_ALLOWLIST` in the test.
6. Add the locale to the review checklist below and get a native-speaker
   review in situ on staging (`NEXT_PUBLIC_DEFAULT_LOCALE=<tag>`).

## Adding or changing a string

1. Add the key to `src/i18n/en.ts` (semantic name, English value).
2. Add the same key to every other locale file — `tsc` enforces this.
3. Use it: `const t = useT(); t("my.key")` in components, or
   `t(locale, "my.key")` outside React.
4. Never write the English text inline in JSX. The lint guard below fails
   the build if you do.

## Lint guard

`eslint.config.mjs` applies to `src/components/**/*.tsx` and
`src/app/**/*.tsx` (tests excluded):

- `react/jsx-no-literals` (`noStrings: true`, `ignoreProps: true`) — rejects
  JSX text children and `{"literal"}` expression containers. `ignoreProps`
  is `true` because with `false` the rule reports every string attribute
  (`className`, `type`, svg `d`, …) and has no per-attribute filter.
- `no-restricted-syntax` selectors — reject string literals in user-facing
  attributes (`aria-label`, `placeholder`, `title`, `alt`, `tooltip`, …) and
  in ternary / logical expressions inside JSX, which `jsx-no-literals`
  does not see.
- `allowedStrings`: `·` (glyph), `BT Servant`, `BTS Web` (product names).
  Add to this list, with a comment, only for strings that are genuinely not
  translation targets. Do not `eslint-disable` inline.

## Review checklist for a new locale or new strings

- [ ] Every key present in every locale file (`npm run typecheck`,
      `npm test`).
- [ ] No value is byte-identical to English unless it is a proper noun on
      the allow-list.
- [ ] Register and tone match the product voice: natural, not machine-stiff;
      for pt-BR the "você" form.
- [ ] Suggestion-chip prompts read as something a native speaker would
      actually type to the model, not as label translations.
- [ ] Punctuation and ellipses follow the language's conventions.
- [ ] Strings fit their controls (chips, menu items, aria labels) without
      truncation on a narrow viewport.
- [ ] `"[Voice message]"` and the status keyword heuristic are untouched.
- [ ] Reviewed in situ on staging by a native speaker, not only in the diff.
